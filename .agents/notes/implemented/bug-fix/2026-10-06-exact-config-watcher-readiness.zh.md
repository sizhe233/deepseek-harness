# Agent Note: 精确配置监视器在 macOS 以外保留原生就绪语义

Status: implemented

[English](2026-10-06-exact-config-watcher-readiness.md) | 中文

## 问题

fork 为了保留 macOS 上快速替换配置文件的行为，强制所有精确配置监视器使用轮询。在 Linux 上，注册完成后立即创建配置文件可能丢失通知，最初不存在的父目录下的创建操作也会受影响。Chokidar 扫描父目录后安装 `fs.watchFile` 轮询器，并在没有等待 Node 异步建立初始轮询基线的情况下发出 `ready`。[用户补丁投递决策](../testing/2026-09-09-user-patch-hmr-test-delivery.zh.md)记录了这一限制。事件丢失后再延长等待时间也无法恢复它。

资源释放测试还会固定等待 250 ms 再关闭监视器。这个间隔不能证明第一次刷新被阻塞时，第二个文件系统事件已经到达 HMR（热模块替换）。

## 决策

精确配置监视器仅在 macOS 上强制使用轮询。其他平台使用原生监视，除非调用方明确请求轮询。保留的缺失父目录深度与 50 ms 轮询间隔维持 macOS 兼容措施；普通模块监视器不变。轮询的就绪语义仍仅限于 Chokidar 的初始扫描，不承诺 Node 已完成轮询基线的建立。

[HMR 配置测试](../../../../packages/boot/app-boot/tests/hmr-config.spec.ts)保留真实文件系统监视器，并显式断言后端选择。资源释放用例等待精确监视器上的 `change` 监听器，该监听器注册在 HMR 监听器之后，从而证明第二次刷新已在 dispose（资源释放）前入队。Context 清理先于临时根目录删除执行，设置失败时也是如此。

## 考虑过的替代方案

**继续在所有平台强制轮询。** 拒绝，因为在 Chokidar 发布就绪状态时原生监视器已经安装的平台上，该兼容措施反而引入了轮询启动缺口。

**在所有平台取消轮询。** 拒绝，因为在没有 macOS 行为证据的情况下，这会移除 fork 针对 macOS 快速替换操作的兼容措施。

**增加固定等待时间或重复写入。** 拒绝，因为时间流逝不能确认监视器已经启动或刷新已经入队，而重复写入会掩盖单次编辑的丢失。

**在 HMR 配置套件中 mock 原生投递。** 拒绝，因为该套件负责验证真实文件系统投递；独立的用户补丁事务测试已经控制投递，同时保留真实的 HMR 和 Include。

## 影响

Linux 上的配置创建和资源释放断言依赖可观察的原生就绪状态与事件投递。负向对照会拒绝无条件轮询和丢弃已排队刷新的实现。独立并发进程验证每个测试对目录与监视器的独立管理。Linux 验证不能确立 macOS 或 Windows 的投递保证；它们的现有行为仍由各自的平台测试任务验证。没有修改 Session、模型输出、依赖版本或公共 API。
